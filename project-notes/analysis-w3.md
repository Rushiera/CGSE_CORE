### 1.2 线的划分：variant × round 递增链

### 1.3 三档停滞口径

| 口径 | 定义 | 修的病 |
|:--:|:--|:--|
| **P** | 与**上一轮** missing 比；UNKNOWN 记停滞（= 上游 `:235` 语义） | 无（上游原口径） |
| **Q** | 与该线**历史最优** missing 比 | P 会因「回落再降」误判有进展 |
| **R** | 与该线**历史最优缺口密度**（missing/recipes）比 | P/Q 都受「视图扩张 → 缺口绝对值暴涨」污染 |

## 四、分叉判据裁决

### 4.1 §十二 的判据与两种读法

> 「无效推进占比 > 30% → 走『提前放弃』，收益上限 = 该占比；< 30% → 步数本身是必要的，方向转向『提高每步信息量』。」

判据没写分母。两种读法给出**相反结论**：

| 分母 | 读数（R 档） | 判据裁决 |
|:--|--:|:--|
| round spent（轮次可归因面） | 47.6% | **>30% → 提前放弃** |
| 总 work（整请求） | 18.8% | **<30% → 提高每步信息量** |

### 4.2 裁决：取 round spent 分母 → 走「提前放弃」

**论证**（不是偏好，是归因链）：

1. 「提前放弃」能省下的成本 = 停滞轮的 spend **+ 该轮触发的轮外子阶段**（`region_counts` / `region` / `compile` / `count_*`）。这些子阶段按轮次触发（每轮一次 compile、若干次 region_counts）。
2. round spent 只覆盖 39.5% 总 work，其余 60.5% 是这些被轮次驱动的子阶段。
3. 若用「总 work」做分母，等于把这 60.5% 的轮外成本**算成非停滞**——分子只算轮内、分母含轮外，比例系统性偏低。
4. 等价换算：停滞轮对应的「轮内 + 轮外」成本 ≈ 6.26M × (38.02M / 15.0M) ≈ **15.9M = 41.7% 总 work**，与占 round spent 同一比例。

**结论：41.7%（P）/ 47.6%（R）> 30% → 走「提前放弃」。**

### 4.3 敏感性（裁决的脆弱点）

- 若第 1 条的「轮外成本随轮次线性」不成立（例如 compile 只跑一次、region_counts 与轮次弱相关），则分子扩大系数变小，读数向 18.8% 靠拢 → 裁决反转。
- **本轮无法验证这条前提**：时间片轮转让轮外成本不可按轮切分（§10.5 已知的近似）。
- 另一个摆动源是**停滞定义**：P 41.7% / Q 60.4% / R 47.6%，跨度 18.7 个百分点——三档都 >30%（round 分母下），所以裁决对这一维**稳健**；对分母维**不稳健**。

## 五、机制事实修正：`stalledRounds` 不是放弃判据

`analysis-attribution.md` §11.3 记「放弃判据已存在，阈值宽松」。本轮源码复核：**不存在放弃判据**。

| 位置 | 事实 |
|:--|:--|
| `GraphStockViewWork.java:232-237` | `stalledRounds` 只累计与重置，无分支消费它做退出 |
| `GraphStockViewWork.java:581-585` | 唯一消费点 `estimatedRepairCost() = outstanding × (1+missingKeys) × (1+min(8, stalledRounds))` |
| `GraphStockViewPortfolio.java:177-178` / `:322-325` | 用于**视图选择**：每 4 次 dispatch 有 3 次选 `estimatedRepairCost()` 最低者 |
| `GraphStockViewPortfolio.java:307-329` `next()` | 公平轮转 + 优先级偏好；`eligible()` 不含停滞条件 → **停滞视图永不被淘汰**，只会被排到后面 |

**实测印证**：V2.0 连续 8 轮停滞（`stalledRounds` 已达上限 8）仍继续被调度并最终解出——因为 `missingKeys()=1` 使其代价估算（≈18× roundCost）低于 V6（≈90×），反而**优先**。

**执行含义**：候选 D「`stalledRounds` 阈值收紧」不可行（无阈值可紧）；「提前放弃」= **新增淘汰机制**（在 `next()` 的 `eligible()` 面加 `retired` 判定），不是改常量。

## 七、诚实边界

1. **n=1**：全部数字来自单请求（seed=73 / amount=1000 / 40M 预算）。11 条线里有 5 条 ≤5 轮，样本极薄。
2. **成功线只有 1 条**：任何「保住成功线、砍掉失败线」的判据都是单例拟合，**不能称为已验证**。
3. **分母前提未验**：§4.2 第 1 条（轮外成本随轮次线性）是推断，不是实测——时间片轮转让它不可直接切分。
4. **停滞 ≠ 无效**：停滞只说明 `missing_keys` 未创新低。V2.0 的 8 个停滞轮是**必要的**（它靠这些轮磨掉最后 1 个缺口）。「无效推进」的严格定义需要件 3 的步级前沿采样。
5. **R 档密度是代理**：`missing/recipes` 假设缺口与 recipes 同尺度，未验证；它只用来抵消「扩张即上涨」的系统偏差。
6. **`spent` 的边界**：`usedWork() - completedWork` 是视图自身 work 差，不含其它视图的时间片；轮外子阶段不在其中（这正是分母争论的根源）。
7. **UNKNOWN 轮**（11 条 / 1.37M）在本报告中未定性：它们既非有效推进也非停滞（无缺失序列），单列在 §3.1 的并集口径里。

### 9.1 C 案：样本从 1 请求扩到 15 请求

用 w2 变体（`spent=` + `diagnostics` 插桩）跑 7 个数据集面共 **15 个有轮次记录的请求**（`build/d4/{emitter,funded-1..3,miracle-a/*}` + `d4-smoke`）：

| 项 | 值 |
|:--|--:|
| 请求 | 15（另有 5 个请求无轮次记录，已剔除） |
| 线 | 161 |
| 总 work | 183,188,934 |
| round spent | 90,528,076（占总 work 49.4%） |
| 成功线 / 失败线 | 15 / 146（每请求恰 1 条成功线） |

**停滞占比（全域）**：

| 口径 | 停滞轮 | spent | 占 round | 占总 work |
|:--|--:|--:|--:|--:|
| P | 812 | 47,841,961 | 52.8% | 26.1% |
| Q | 958 | 65,534,262 | 72.4% | 35.8% |
| **R** | 605 | 37,023,317 | **40.9%** | 20.2% |

R 档 40.9% 仍 >30%——**分叉裁决「提前放弃」在多请求上维持**（单请求 47.6% → 多请求 40.9%，略降但同向）。

**成功线的缺口分布（决定缺口门 M）**：成功线停滞轮的 `missing_keys` 全值 =

### 9.3 根因：判定「完成」是调度结构的耦合点

`GraphStockViewPortfolio.step()`：

- `:150-152`——`done` 或时间片用满 → `next()`；`original.live == 0 && quantitative.live == 0` → **`viewsComplete = true`**
- `:78-91`——`work >= until || viewsComplete` → 先 `addQuantitativeViews()`（variant 8/9 入场），再 `pause()`（交还控制权给上层）或 `complete = true`

因此：

- **A1（真撤退）**：视图数减少 → 原视图族更早全 done → `addQuantitativeViews()` 与 `pause()` 提前 → 部分请求反而更晚解出（预算被重新谈判拉长）。收益方向不稳定，净 +7.7%。
- **A2（只跳过）**：retired 视图永不 done → `live` 永不为 0 → `viewsComplete` 永假 → **量化视图（variant 8/9）永不入场**，`pause()` 也不发生 → 一路烧到预算上限（`miracle-quantity x1000` 直接 `SEARCH_LIMIT`）。+42% 与 ERROR 同源。

**结论：在现有调度里，「放弃一条视图」与「让视图族完成」是同一件事**——没有第三条路能既省时间片、又不改变入场/交接时序。

### 10.1 D：首轮特征不能分离成功线与失败线

用 15 请求 / 161 条线（每条线 = 一个视图实例）的首轮特征做分离度检验：

| 组 | n | 首轮 missing p50/p90/max | 首轮 recipes p50/p90 | 首轮密度 p50/p90 |
|:--|--:|:--|:--|:--|
| 成功线 | 15 | 1 / 20 / 36 | 3 / 88 | 0.516 / 1.000 |
| 失败线 | 145 | 1 / 18 / 120 | 1 / 39 | 0.630 / 1.000 |

**分布完全重叠**。更硬的一刀——把每个请求的线按首轮密度升序排，看成功线排第几：

- 名次 p50 = **10**（每请求 10–15 条线），p90 = 11，**只有 1/15 个请求的成功线排第 1**
- 每请求只留首轮密度最小 1 条 → 保住 **1/15** 个请求，误伤成功线 14 条
- 阈值 `密度 ≤ 0.002` → 保 2 个请求；`≤ 0.05` → 保 4 个

**结论：D 判死。** 首轮是侦察轮——所有视图都还没展开，成功与失败的差异只在后续推进中显现。任何"入场即筛"的判据都会砍掉绝大多数成功线。

（口径与原始表：`.local/w3/out/d.txt`，脚本 `w3_d.py`。）

### 10.2 B：每轮成本与产出无关，改造对象是轮级重建而非单步算子

先记一条**方法失败**：想用 `wstack-checkhist.tsv` 按轮区间切 check 数，实测不可行——note 的 `work@` 是采样点，同一轮的工作分散在多个 note 间隔里（时间片轮转 + 视图交错），按区间求和会出现「spent 2,877 但 checks 1,466,346」（check 数超过 spend 本身）。脚本保留在 `w3_b.py`（头部标作废），有效口径换成 `w3_b2.py`。

**可靠口径 ①：轮 spend 与产出的关系**（funded-3，同一请求内比较）

| 组（spent ≥ 100K 的轮） | 轮 | spend 均值 | p25 | p75 |
|:--|--:|--:|--:|--:|
| 缺口下降轮 | 14 | 421,615 | 365,200 | 436,536 |
| 停滞轮 | 16 | **368,614** | 355,338 | 402,639 |

**比值 0.87**——停滞轮的成本与有产出的轮几乎相同。轮内 spend 的变异系数：`V2.0` **0.19**、`V6.0` **0.21**（成本几乎恒定，与每轮做了什么无关）。

→ **每轮的成本由「每轮固定动作」决定，不由「推进了多少」决定。**

**可靠口径 ②：轮间固定 stage 组合**（64 个轮间隔）

| stage | 出现在多少比例的轮间隔 | §10.2 的 work 占比 |
|:--|--:|--:|
| `region_counts` | **81.2%** | 46.2% |
| `support_neighborhood` | 48.4% | — |
| `stock_view` | 28.1% | 21.4% |
| `region` | 23.4% | 12.0% |
| `plan_flow_pruning` | 20.3% | — |
| `plan_egraph` | 15.6% | 1.6% |

三者对齐：**每 1.2 轮就要重跑一次 `region_counts`，而它单项吃掉 46% 的 work**。

**结论：B 的落点不是「合并小步 / 换算子」**（§11.5 已封顶循环内 check 合并 ≤13.1%，那 85% 的步数税是每方法入口的检查点，与推进步数一一对应），而是**每轮重建**：

- `region_counts` 每轮对 1146 个 region 重扫计数（`selected_counts_blocked` / `model_limit`）
- `compile` 每轮重建（`choice=N; recipes≈2999; regions≈1146`）
- `region` / `region_solve` 每轮重跑，绝大多数返回 `no_witness`

改造成本：**架构级**——跨轮增量复用（cache 计数模型 + region 级失效判定）。风险面：
1. 健全性——复用的前提是「未受本轮 source 变更影响的 region 才可复用」，判定错即可能给出错误计数；
2. 与 A 同源的结构问题——复用改变的是「谁在什么时候花 work」，仍要碰 `viewsComplete` / `pause()` 的时序。
